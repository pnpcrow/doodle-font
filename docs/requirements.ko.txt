이 요구사항을 반영하면 앱의 범위는 **“여러 언어의 글자를 만드는 폰트 저작툴”에서 “문자·문자열·공백·이모지의 표시 형태를 함께 설계하는 저작툴”**로 확장됩니다.

따라서 앞서 확장 기능으로 두었던 **컬러 글리프 편집, 유니코드 문자열 매핑, 템플릿 원본 관리·복원은 기본 설계에 포함**해야 합니다.

다만 구현 명세에서는 **“어떤 문자인가”와 “어떤 그림으로 표시하는가”를 분리**해야 합니다. 특히 ‘유니코드 기본 그림으로 복원’은 실제로는 **선택한 템플릿의 원본으로 복원하는 것**과 **현재 시스템의 기본 표시로 돌아가는 것**으로 나누는 것이 정확합니다. Unicode에 실린 업체별 컬러 이모지는 설명용이며, Unicode가 모든 시스템에 공통으로 사용할 단일 컬러 원본을 제공하는 것은 아닙니다. [Unicode](https://www.unicode.org/emoji/images.html)

## 1. 지원 문자 범위: 언어별 목록과 유니코드 기반 편집을 함께 제공

지원 범위는 말씀하신 내용을 기준으로 잡고, 편집에 필요한 세부 항목을 다음처럼 구성하는 것을 제안합니다.

| 분류 | 지원 대상으로 명시할 내용 | 함께 필요한 편집 기능 |
|---|---|---|
| 알파벳 | 라틴 알파벳 대·소문자, 숫자, 구두점. 확장 라틴 문자는 선택 가능한 문자 집합으로 추가 | 악센트·결합 부호, 반복 획·부품 재사용 |
| 한글 | 완성형 음절, 자모. 옛한글은 별도 문자 집합으로 확장 가능하게 설계 | 초성·중성·종성 조합, 위치별 자모 변형, 음절별 예외 |
| 한국한자 | 한국어용 한자 문자 집합과 한국어용 자형 | 한국어 기준 자형 관리, 부수·구성 요소 재사용 |
| 가나 | 히라가나·카타카나, 작은 가나, 탁점·반탁점, 장음, 전각·반각 형태 | 결합 부호 배치, 폭·높이 조정, 세로쓰기용 형태 |
| 일본한자 | 일본어용 한자 문자 집합과 일본어용 자형 | 일본어 기준 자형, 이체자, 한국어용 자형과 비교 |
| 기호·그림문자 | 문장 부호, 수학 기호, 화살표, 도형, 이모지 등 | 단색·컬러 편집, 이미지 교체, 템플릿 적용 |
| 유니코드 문자열 | 단일 코드포인트뿐 아니라 여러 코드포인트로 구성된 표시 단위와 사용자 지정 문자열 | 시퀀스 매핑, 결합·합자 처리, 원문 보존 |
| 사용자 정의 문자 | 자체 아이콘이나 별도 문자 | 사적 사용 영역 매핑, 사용자 정의 이름·설명 |

여기서 언어별 목록은 편리하게 작업 대상을 선택하기 위한 **문자 집합 프리셋**이고, 내부 데이터는 특정 언어 목록에 묶이지 않도록 하는 편이 좋습니다. 예를 들어 사용자가 문장을 붙여 넣으면 그 문장에 필요한 문자·시퀀스를 추출하고, 이미 작성된 것과 미작성인 것을 구분하도록 합니다.

### 한국한자와 일본한자는 ‘문자 목록’만 나누면 부족합니다

Unicode에서는 여러 지역에서 사용하는 한자가 같은 코드포인트로 통합되어 있으면서도, 지역에 따라 선호되는 글리프 모양이 다른 경우가 있습니다. 따라서 같은 코드포인트에 한국어용·일본어용 자형을 별도로 보관할 수 있어야 합니다. [Unicode](https://www.unicode.org/faq/han_cjk.html)

권장 요구사항은 다음과 같습니다.

> 동일한 한자에 한국어용 자형과 일본어용 자형을 별도로 등록·편집할 수 있어야 한다. 한쪽 자형을 수정하거나 AI로 생성해도 다른 지역 자형을 자동으로 덮어쓰지 않는다.

출력에서는 한국어용·일본어용 폰트를 따로 만들거나, 한 폰트 안에 지역별 자형을 넣고 언어 정보에 따라 전환하는 방식을 지원할 수 있습니다. OpenType의 `locl`은 이러한 지역별 자형 대체를 위한 기능입니다. 다만 사용하는 앱이 적절한 언어 정보를 전달해야 하므로, 별도 폰트 출력 방식도 유지하는 것이 좋습니다. [Microsoft Learn](https://learn.microsoft.com/en-us/typography/opentype/spec/features_ko?utm_source=chatgpt.com)

## 2. ‘유니코드 문자열’을 하나의 편집 대상으로 취급

**글리프 하나를 반드시 코드포인트 하나에만 대응시키는 구조로 만들면 안 됩니다.**

예를 들어 하트의 이모지 표시에는 표시 선택자가 붙을 수 있고, 직업 이모지는 여러 문자와 ZWJ라는 연결 문자가 합쳐져 하나의 그림으로 표시될 수 있습니다. Unicode는 이러한 이모지 시퀀스를 정의합니다. [Unicode](https://www.unicode.org/reports/tr51/)

```text
단일 문자
    A
    가

여러 코드포인트로 구성되는 표시
    하트 + 이모지 표시 선택자
    사람 + ZWJ + 직업을 나타내는 문자

사용자 정의 문자열 매핑
    지정한 문자열 → 사용자가 만든 하나의 글리프
```

이에 따라 편집 화면에는 **화면에 보이는 결과**, **원본 문자열**, **코드포인트 목록**을 함께 표시하도록 제안합니다.

일반적인 선택·이동·삭제에서는 사람이 한 글자로 인식하는 묶음을 다루고, 고급 편집에서는 그 내부의 코드포인트까지 확인할 수 있게 합니다. Unicode의 확장 자소 클러스터 규칙은 이러한 편집 단위를 다루며, 일반 교환용으로 권장되는 이모지 시퀀스는 각각 하나의 클러스터에 속합니다. [Unicode](https://www.unicode.org/reports/tr29/?utm_source=chatgpt.com)

추가 명세에는 다음 내용을 포함해야 합니다.

**원문 보존:** 가져온 문자열을 임의로 정규화하거나 표시 선택자·연결 문자를 제거하지 않습니다. 정규화나 동등한 표현의 연결은 별도 기능으로 제공합니다.

**변형별 관리:** 텍스트형 하트와 이모지형 하트, 피부색이 다른 이모지, 여러 사람이 포함된 조합 등을 별도 대상으로 관리합니다. 하나를 수정했을 때 관련 변형 전체를 바꿀지는 사용자가 선택합니다.

**표준 시퀀스와 사용자 정의 매핑 구분:** Unicode에서 정의한 이모지 조합과 사용자가 임의로 등록한 ‘문자열 → 그림’ 규칙을 같은 것으로 표시하지 않습니다.

폰트 출력 시에는 단일 문자 매핑, 변형 선택자 매핑, 여러 글리프를 대체하는 규칙이 서로 다른 방식으로 처리됩니다. 대표적으로 `cmap`, `cmap format 14`, `GSUB`가 사용됩니다. 따라서 앱 내부에서 문자열을 그림으로 표시하는 데 성공했더라도, 모든 외부 앱에서 임의의 문자열 치환이 그대로 동작한다고 보장해서는 안 됩니다. [Microsoft Learn](https://learn.microsoft.com/en-us/typography/opentype/spec/cmap)

## 3. 공백도 편집하되, ‘빈칸’의 종류를 구분

말씀하신 **공백 재정의는 기능에 포함**하는 것이 맞습니다. 다만 다음 항목은 서로 다르게 처리해야 합니다.

### 실제 공백 문자

일반 공백, 줄바꿈 방지 공백, 전각 공백 등을 선택하여 **폭을 조정하거나, 원하는 경우 보이는 모양을 부여하는 편집 기능**을 제공합니다.

예를 들어 공백의 진행 폭을 넓히거나, 장식용 폰트에서 공백 자리에 작은 표시를 그리는 작업입니다. 단, 외부 앱이 공백을 축약하거나 별도로 배치할 수 있으므로, 미리보기와 실제 사용 환경을 구분해 시험해야 합니다.

또한 **모양·폭을 바꾸는 것과 공백의 텍스트 기능을 바꾸는 것은 별개**입니다. 일반 공백과 줄바꿈 방지 공백은 줄바꿈 동작이 다르며, 그 차이를 단순한 글리프 편집으로 없애는 기능으로 설명하면 안 됩니다. [Unicode](https://www.unicode.org/reports/tr14/)

### 탭·줄바꿈·연결 문자

탭과 줄바꿈은 일반적인 그림 글자처럼만 다룰 수 없습니다. 애플리케이션의 레이아웃 처리와 제어 문자 해석이 관여하기 때문입니다. [Unicode](https://www.unicode.org/versions/Unicode17.0.0/core-spec/chapter-23/)

따라서 편집기에서는 이들을 확인할 수 있는 **비출력 문자 표시 모드**를 제공하되, 화면에 보이는 탭 화살표나 줄바꿈 표시를 그대로 폰트의 출력 글리프로 취급하지 않도록 합니다. 이모지 조합에 쓰이는 ZWJ도 일반 빈칸으로 처리하지 않습니다. [Unicode](https://www.unicode.org/reports/tr51/)

### 아직 작성하지 않은 칸과 사용자 정의 문자

**미작성 글리프**, **의도적으로 비워둔 글리프**, **해당 폰트에서 지원하지 않는 문자**는 별도 상태로 관리하도록 제안합니다. 그렇지 않으면 ‘빈칸을 유지하려고 만든 것’을 AI가 미작성으로 판단해 채울 수 있습니다.

Unicode에 없는 자체 아이콘이나 문자는 사적 사용 영역인 **PUA**에 매핑하는 기능을 제공합니다. PUA는 사용자 간 약속에 따라 의미를 정할 수 있도록 마련된 영역입니다. [Unicode](https://www.unicode.org/glossary/?utm_source=chatgpt.com)

## 4. 이모지 교체와 복원은 ‘원본 보존형 편집’으로 구현

이모지를 다른 그림으로 교체하는 기능은 다음 흐름으로 구성하면 됩니다.

```text
문자 또는 이모지 시퀀스 선택
    ↓
기준 템플릿 선택
    ↓
직접 그리기 / 이미지 가져오기 / 부품 조합 / AI 생성
    ↓
기존 그림과 비교
    ↓
사용자 그림 적용
```

이때 **그림을 교체해도 연결된 문자나 문자열은 유지**하는 것이 기본 동작입니다.

예를 들어 웃는 얼굴 이모지 자리에 꽃 그림을 넣는 것은 가능하도록 만들 수 있지만, 그 텍스트가 Unicode상 꽃 문자로 바뀌는 것은 아닙니다. 다른 폰트로 표시하면 다시 해당 코드에 대응하는 얼굴이 나타날 수 있습니다. 즉 이 기능은 기본적으로 **문자의 시각적 표현을 바꾸는 기능**입니다. [Microsoft Learn](https://learn.microsoft.com/en-us/typography/opentype/spec/cmap)

### 복원 명령을 세 가지로 구분

| 명령 | 동작 |
|---|---|
| **템플릿 원본으로 복원** | 편집을 시작할 때 선택한 템플릿의 특정 버전으로 복원 |
| **사용자 기준 버전으로 복원** | 사용자가 따로 저장한 승인본이나 기준 디자인으로 복원 |
| **사용자 정의 해제·시스템 기본으로 표시** | 앱의 사용자 정의 그림을 적용하지 않고 현재 시스템의 기본 렌더링 사용 |

여기서 ‘템플릿 원본으로 복원’은 최근 작업 한 번을 취소하는 Undo와 달라야 합니다. 여러 번 수정하고 프로젝트를 닫았다가 다시 열어도 원본으로 돌아갈 수 있도록 설계합니다.

권장 데이터 구조는 다음과 같습니다.

```text
변경하지 않는 템플릿 원본
    + 사용자가 적용한 수정본
    + AI 생성 후보
    + 현재 채택한 결과
```

템플릿 이름뿐 아니라 **제공자, 버전, 원본 식별자, 복원에 필요한 데이터의 위치**까지 기록합니다. 새 템플릿 버전이 나와도 이전 프로젝트의 기준 원본을 자동으로 바꾸지 않습니다.

원본 데이터를 보관할 수 있는 자산은 허용된 범위에서 보존하고, 외부 참조만 가능한 자산은 원본을 찾지 못했을 때 그 사실을 알리도록 합니다. 다른 버전의 그림을 조용히 가져와 ‘원본 복원 완료’로 표시하면 안 됩니다.

### 시스템 기본 표시와 폰트 파일 출력은 분리해야 합니다

앱 안에서 시스템 기본 이모지를 보여주는 것과, 출력한 폰트 파일에 그 그림을 넣는 것은 다릅니다. 웹의 경우에도 대체 폰트 선택은 폰트 목록·지원 문자·클러스터 매칭 등에 따라 이루어지며, 이모지 표시와 폰트 대체의 상호작용에는 구현 의존적인 부분이 있습니다. [W3C](https://www.w3.org/TR/css-fonts-4/?utm_source=chatgpt.com)

따라서 출력은 다음 두 방식으로 구분하는 것이 좋습니다.

**그림을 포함하는 출력:** 필요한 글리프를 실제 폰트에 넣습니다. 포함하는 템플릿 자산의 배포 권한을 확인해야 합니다.

**사용자 제작 부분만 출력:** 나머지 문자는 사용 환경의 다른 폰트에 맡깁니다. 이 경우 다른 기기에서도 동일한 기본 그림이 나온다고 보장하지 않습니다.

또한 폰트를 제작·설치하는 것만으로 **모든 앱이나 상대방 기기의 이모지를 일괄 교체하는 기능**까지 제공하는 것은 아닙니다. 실제 표시에는 해당 환경의 폰트 선택이 관여합니다. [W3C](https://www.w3.org/TR/2018/REC-css-fonts-3-20180920/?utm_source=chatgpt.com)

## 5. Apple·Samsung 템플릿은 지원하되, 자산 제공 권한을 별도 관리

**시스템별 이모지를 템플릿으로 선택하는 기능 자체는 기획에 포함할 수 있습니다.** 다만 실제 업체 자산을 앱에 동봉하여 편집·내보내기까지 허용하는 것은 별도 문제입니다.

Unicode는 업체별 그림의 권리가 각 소유자에게 있으며, 사용 허가는 Unicode가 아니라 해당 업체에 문의해야 한다고 명시합니다. 따라서 Unicode 표에서 이미지를 가져올 수 있다는 사실을 재배포 허가로 간주해서는 안 됩니다. [Unicode](https://www.unicode.org/emoji/images.html)

Apple의 경우 특히 **App Store 심사 지침 5.2.5에 앱과 확장 프로그램이 Apple 이모지를 포함해서는 안 된다는 조항**이 있습니다. Apple 자산을 편집용 템플릿으로 동봉하는 계획에는 이 제약을 반영해야 합니다. [Apple Developer](https://developer.apple.com/app-store/review/guidelines/)

Samsung의 이모지 자산을 이 앱에 동봉하고 수정·재배포하는 것까지 허용하는 공식 공개 라이선스는 이번 확인 범위에서는 찾지 못했습니다. **금지라고 단정하는 것이 아니라, 기본 제공을 확정할 권한 근거가 아직 없는 상태**로 두는 것이 정확합니다.

따라서 템플릿 구조는 다음처럼 제안합니다.

| 템플릿 유형 | 제공 방식 |
|---|---|
| 재사용 조건이 명확한 공개 자산 | 조건을 준수하여 기본 제공하거나 추가 팩으로 제공 |
| Apple·Samsung 등 업체 자산 | 권한과 배포 조건을 확인한 경우 해당 조건에 맞춰 제공 |
| 사용자가 가져온 자산 | 출처·권리 정보를 기록하고, 가져왔다는 사실만으로 재배포 가능 판정을 내리지 않음 |
| 현재 시스템 표시 | 시스템에서 렌더링한 결과를 보는 모드. 편집 가능한 원본 자산 제공과 구분 |

공개 템플릿 후보로는 **Noto Emoji와 OpenMoji**를 검토할 수 있습니다. Noto Emoji 저장소는 폰트와 이미지 자산의 라이선스를 구분하며, OpenMoji 그림은 CC BY-SA 4.0으로 제공됩니다. 따라서 ‘오픈소스이므로 아무 조건 없이 사용 가능’으로 묶지 않고, 정확한 자산과 버전별 조건을 관리해야 합니다. [GitHub](https://github.com/googlefonts/noto-emoji?utm_source=chatgpt.com)

템플릿별로는 최소한 **표시·수정·폰트 포함·원본 재배포·출처 표시 조건**을 기록하도록 합니다. AI 참고 자료로 외부 서버에 전송하는 작업도 별도로 구분하는 편이 좋습니다.

## 6. 이번 요구사항으로 기본 기능에 추가되는 것

### 컬러·이미지 글리프 편집

단색 윤곽뿐 아니라 **컬러 벡터, 비트맵 이미지, 투명도, 레이어, 팔레트**를 관리해야 합니다. 가져온 이미지의 원본은 보존하고, 벡터화나 단색화는 선택적인 변환으로 제공합니다.

OpenType은 컬러 벡터나 비트맵 등 여러 글리프 표현 방식을 지원합니다. 따라서 프로젝트 내부의 편집 데이터를 특정 출력 형식 하나에 종속시키기보다, 출력 단계에서 대상 형식으로 변환하도록 설계하는 것이 좋습니다. [Microsoft Learn](https://learn.microsoft.com/en-us/typography/opentype/spec/otff)

예를 들어 `COLR/CPAL`은 컬러 글리프와 팔레트를 다루고, `sbix`는 비트맵 글리프 데이터를 담습니다. 실제 지원할 출력 형식과 대상 환경은 별도 호환성 시험으로 결정해야 합니다. [Microsoft Learn](https://learn.microsoft.com/en-us/typography/opentype/spec/colr?utm_source=chatgpt.com)

### 대규모 문자 집합과 분할 출력

한글·한자·이모지·지역별 대체 자형을 함께 다루므로, **프로젝트가 관리하는 전체 글리프 수와 폰트 파일 하나에 넣는 글리프 수를 분리**해야 합니다.

일반적인 OpenType의 `maxp.numGlyphs`는 16비트 값이므로 한 폰트 페이스의 글리프 수는 최대 65,535개입니다. 이는 문자 수가 아니라 대체 자형·부품 등까지 포함한 글리프 수의 한계입니다. [Microsoft Learn](https://learn.microsoft.com/en-us/typography/opentype/spec/maxp)

따라서 문자 집합별·언어별 분할 출력, 필요한 문자만 내보내기, 출력 전 글리프 수 계산을 기본 명세에 넣는 것이 좋습니다. 문자 목록 화면도 전체 글리프를 한꺼번에 렌더링하지 않도록 설계합니다.

### AI 생성의 대상과 보호 범위

기존에 정한 OpenAI 호환·Anthropic 호환 API 구조는 유지하면서, 생성 요청에 다음 정보를 포함하도록 확장합니다.

> 대상 문자·정확한 시퀀스, 한국어/일본어 등 자형 기준, 참고 글리프, 단색/컬러 여부, 템플릿 사용 범위, 수정 금지 대상.

예를 들어 일본한자 생성 요청에 한국어용 자형을 무조건 정답으로 사용하거나, 한 이모지를 수정하면서 다른 피부색·조합까지 자동으로 덮어쓰지 않도록 합니다.

API가 없어도 직접 편집, 기본 선 보정, 도형 복제·조합, 권한이 허용된 템플릿 적용, 그림 교체·복원은 모두 가능해야 합니다. AI는 그 위에서 **미작성 항목 생성과 디자인 변형을 보조**합니다.

## 7. 개발 에이전트용 프롬프트에 추가할 요구사항 문안

현재 단계에서는 기존 요구사항에 다음 내용을 추가하면 됩니다.

> **지원 문자와 매핑**
>
> 라틴 알파벳, 한글, 한국한자, 히라가나, 카타카나, 일본한자, 각종 기호와 이모지를 지원한다. 언어별 문자 집합 프리셋을 제공하되 내부 데이터 모델을 특정 문자 집합에 고정하지 않는다. 단일 코드포인트뿐 아니라 여러 코드포인트로 구성된 시퀀스와 사용자 지정 문자열을 편집 대상으로 관리한다.
>
> 문자·문자열의 식별 정보와 글리프의 시각적 데이터를 분리한다. 동일한 문자에 여러 지역별 자형과 디자인 후보를 연결할 수 있어야 한다. 한국한자와 일본한자의 자형을 별도로 관리하고, 한쪽의 편집·AI 생성이 다른 쪽을 자동으로 덮어쓰지 않도록 한다.
>
> **공백과 사용자 정의 문자**
>
> 공백 글리프의 폭과 시각적 형태를 편집할 수 있도록 한다. 실제 공백 문자, 제어 문자, 미작성 글리프, 의도적으로 비운 글리프, 지원하지 않는 문자를 구분한다. 탭·줄바꿈·문자 연결 기능을 일반 글리프 편집만으로 재정의할 수 있다고 가정하지 않는다. 자체 아이콘을 위한 사적 사용 영역 매핑을 지원한다.
>
> **그림문자 편집과 복원**
>
> 기존 이모지의 표시 그림을 직접 그린 그림, 가져온 이미지, 부품 조합 또는 AI 결과로 교체할 수 있도록 한다. 그림을 바꾸더라도 연결된 문자·시퀀스는 기본적으로 유지한다. 관련 변형 전체에 수정 사항을 전파할지는 사용자가 선택한다.
>
> 템플릿 원본, 사용자 수정본, AI 후보, 현재 채택 결과를 분리해 보존한다. 템플릿 원본 복원, 사용자 기준 버전 복원, 사용자 정의 해제·시스템 기본 표시를 서로 다른 명령으로 제공한다. 원본 복원은 프로젝트를 다시 연 후에도 가능해야 하며, 원본을 확보할 수 없을 때 다른 그림으로 조용히 대체하지 않는다.
>
> **시스템별 템플릿**
>
> Apple·Samsung 등 제공자별 이모지 템플릿을 연결할 수 있는 확장 구조를 제공한다. 다만 해당 자산을 앱에 포함하거나 수정·재배포할 수 있다고 전제하지 않는다. 제공자·버전·출처·이용 조건을 기록하고, 허용 범위에 따라 표시·편집·내보내기 기능을 구분한다. 시스템 기본 렌더링을 보는 기능과 편집 가능한 템플릿 원본을 제공하는 기능을 분리한다.
>
> **출력과 검증**
>
> 단색·컬러·이미지 글리프와 문자열 매핑을 기본 데이터 모델에 포함한다. 프로젝트의 전체 지원 범위와 개별 폰트 파일의 출력 범위를 분리하며, 대규모 문자 집합의 부분·분할 출력을 지원한다.
>
> 미리보기에서는 프로젝트의 실제 글리프와 시스템 대체 폰트로 표시된 글리프를 구분한다. 앱 내부 표시 성공을 외부 앱 호환성으로 간주하지 않으며, 실제 출력 폰트로 지역별 자형, 공백, 이모지 시퀀스, 컬러 표시를 시험한다.
>
> 기존의 AI 미사용 모드와 OpenAI 호환·Anthropic 호환 API 사용 모드를 유지한다. AI는 문자 매핑과 원본·잠금 상태를 보존한 채 생성 후보를 제안해야 하며, API 연결 없이도 편집·교체·복원·저장·출력이 가능해야 한다.

핵심은 **“문자와 문자열은 유지하면서, 그 표현을 사용자가 자유롭게 설계하고 언제든 기준 디자인으로 돌아갈 수 있게 한다”**는 것입니다. 이를 위해 **문자 매핑, 글리프 그림, 템플릿 원본, 사용자 수정본을 처음부터 분리**해 두는 것이 가장 중요한 설계 변경입니다.
